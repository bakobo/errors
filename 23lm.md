# A UI register/localization layer re-renders from code + named args: check the surface makes that easy
kind: todo
created: 2026-08-16T02:31Z

- 2026-08-16T02:32Z WHY. dev/standards/error-handling.md now requires (commit fd33f71 in bakobo/dev) that a
user-facing surface may restate an error in a different vocabulary REGISTER, not just a
warmer voice — heti's library says a lockbox holds no *facet* like that; its TUI says it
knows no *identifier* by that name. Both are right for their reader. The standard's rule is
that such a layer re-renders from the symbolic code and the NAMED values, never by editing
or regex-patching the rendered sentence, and that the same table shape serves localization.

WHAT THIS REPO ALREADY GIVES. ErrorCode carries code/title/detail-template/args/hint, all
static per code, and its docstring already anticipates a localization catalog keying off the
code. BakoboError keeps `entry`, so a translator can recover the named values by zipping
entry.args with code_args.

THE ACTUAL QUESTION. That zip is the awkward part: code_args is positional "in declaration
order" because Python's BaseException owns `args`, so every translation layer re-derives the
name->value mapping by hand, and each one is a place to get the order wrong. Options if this
recurs: a read-only mapping property on BakoboError (named values, derived not stored); a
render(entry_override) helper that formats another ErrorCode's templates with this error's
values; or nothing, if one line at each surface is genuinely fine.

DECIDE WHEN. The first consumer is heti's TUI rewording table (heti this.i draft node N9,
docs/tui-design.md §3). Build it there by hand first; if a second surface wants the same
thing, that duplication is the signal to move it here. Do not add the helper speculatively —
one consumer is not a pattern.
